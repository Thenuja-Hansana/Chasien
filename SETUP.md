# Setting up Chasien from a fresh clone

Everything needed to go from `git clone` to the app running on an Android
phone against a local backend, then (for whoever holds the accounts) the
hosted production project. It's the entry point: each step links to the
doc that covers it in depth.

- **Local development** (sections 1–7) needs no accounts and costs
  nothing. The local backend runs in Docker with test data.
- **Push notifications, builds and the hosted project** (sections 8–9)
  need access to the project's Expo, Firebase, Supabase and Resend
  accounts.

Written for Windows with PowerShell, which is what Chasien is developed
on. On macOS or Linux the commands are the same apart from paths and
`$env:` variables.

---

## 0. What a clone doesn't contain

Some files are kept out of git on purpose. Know which before you start:

| File | What it is | Where it comes from |
|---|---|---|
| `mobile/.env.local` | The app's backend address and public key, local stack | You create it, step 4 |
| `mobile/.env.development.local` | Optional: points the app at the hosted project instead | `docs/hosting.md`, step 8 |
| `supabase/.env.hosted` | The hosted database password and the Resend API key | The project owner's password manager. Only for hosted work |
| `mobile/android/` | The native Android project | Generated by `npx expo run:android`, step 5. Never edited by hand |
| `supabase/.temp/` | The Supabase CLI's link and image-version pins | Generated by the CLI |
| `mobile/chasien-upload-keystore.jks` | The release signing key | The owner's backup. Not needed for development. **Losing it means no updates to a published app**, so keep a copy somewhere other than the laptop |
| The Firebase service account key | Lets Expo deliver Android pushes | Uploaded to the EAS project, never in the repo (section 8) |

`mobile/google-services.json` *is* in git: it's Firebase's client-side
config, not a secret.

**Never commit a secret.** Keys and passwords go in the gitignored files
above. `supabase/config.toml` only names them (`env(RESEND_API_KEY)`).

## 1. Install the tools

| Tool | Version | Notes |
|---|---|---|
| Git | any recent | |
| Node.js | **24** | CI uses 24 (`.github/workflows/mobile-ci.yml`) |
| npm | **11.21 or newer** | `npm install -g npm@latest`. Older npm 11 releases write a `package-lock.json` that CI's `npm ci` rejects (decision-log, 2026-09-22) |
| Docker Desktop | current | Runs the local Supabase stack. On Windows it uses WSL2. The first start downloads several GB of images |
| Android Studio | current | For the Android SDK, `adb` (platform-tools) and its bundled **JDK 21** (`C:\Program Files\Android\Android Studio\jbr`), which native builds need |
| An Android phone | Android with USB debugging | The app runs as a **development build**, not in Expo Go: Expo Go can't do push at all and may not support this SDK (gotchas #6 and #7) |

You don't need to install the Supabase CLI or the Expo CLI: both run
through `npx`. The EAS CLI (`npm install -g eas-cli`) is only for cloud
builds later.

**Put `adb` on your PATH** once, then reopen PowerShell:
```powershell
[Environment]::SetEnvironmentVariable("Path", $env:Path + ";$env:LOCALAPPDATA\Android\Sdk\platform-tools", "User")
```

**Memory:** 8 GB of RAM is tight for Docker plus a native build. Close
what you can during a build, and see gotcha #8 in
`docs/running-locally.md` (it includes turning off VS Code's Java
extension for this folder).

## 2. Clone and install

```powershell
git clone https://github.com/Thenuja-Hansana/Chasien.git chasien
cd chasien\mobile
npm ci
```
Use `npm ci`, not `npm install`, so you get exactly the versions in the
lock file.

---

## 3. Start the local backend

Start Docker Desktop and wait until `docker ps` works (not just
`docker info`: see gotcha #1). Then, from the **repo root**:

```powershell
cd ..            # back to chasien\
npx supabase start -x vector
```

On the first run this downloads the images, creates the database, applies
every migration in `supabase/migrations/` in order, and loads
`supabase/seed.sql`. The seed file holds the test accounts, Rooms, posts and
the two Vault secrets the database uses to reach its Edge Functions.
`-x vector` skips a log shipper the app doesn't need.

Check that the Edge Functions container came up. Joining Rooms, invites,
reports and pushes all depend on it:
```powershell
docker ps --format "{{.Names}}`t{{.Status}}" | findstr chasien
```
If `supabase_edge_runtime_chasien` is missing or `Exited`, run
`docker start supabase_edge_runtime_chasien`.

What's now running:

| Address | What |
|---|---|
| http://localhost:54321 | The API (Auth, database, Storage, Edge Functions) |
| http://localhost:54323 | Supabase Studio, to browse the database |
| http://localhost:54324 | Mailpit, which catches every email the local stack sends |

**Pin the images now** (recommended). `npx supabase` always runs the
newest CLI, and a new CLI pulls new images on the next start. Gotcha #9
explains how to pin the versions you have.

## 4. Point the app at the local backend

```powershell
npx supabase status -o env
```
Create `mobile/.env.local` with the API address and the `ANON_KEY` value
(the long `eyJ…` one):
```
EXPO_PUBLIC_SUPABASE_URL=http://localhost:54321
EXPO_PUBLIC_SUPABASE_ANON_KEY=<ANON_KEY>
```
Use `localhost`, not your computer's network address: the phone reaches
it through a USB tunnel (step 5). The local anon key is Supabase's
standard demo key, the same on every machine, and it only works locally.

---

## 5. Build the app and run it on your phone (first time)

1. **On the phone:** turn on Developer options and USB debugging, plug it
   in, and tap **Allow** on the "Allow USB debugging?" prompt. Then:
   ```powershell
   adb devices -l
   ```
   It should list the phone. If it doesn't, see gotcha #3 (the cable, USB
   mode, Samsung's driver).
2. **The two tunnels.** They let the phone reach Metro (8081) and the
   backend (54321) on your computer. Redo them after every replug:
   ```powershell
   adb reverse tcp:8081 tcp:8081
   adb reverse tcp:54321 tcp:54321
   ```
3. **Build and install the development build** from `mobile\`. This
   takes several minutes the first time:
   ```powershell
   cd mobile
   $env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"
   npx expo run:android
   ```
   It generates `mobile/android/`, builds, installs and opens the app. If
   it hangs right after the `env:` lines, see gotcha #12, which builds
   with Gradle directly.
4. **Make sure the app loads from `localhost`,** not from the network
   address Metro prints (gotcha #2):
   ```powershell
   adb shell am force-stop com.thenujacode.chasien
   adb shell am start -a android.intent.action.VIEW -d "exp+chasien://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081"
   ```
5. **Log in** as `mara@example.com` with password `password123`. All the
   test accounts are listed in `docs/running-locally.md`.

You only need to rebuild when native code changes: a new native module,
native settings in `app.json`, or an Expo SDK upgrade. Everything else
reloads from Metro.

## 6. Every day after that

Start Docker, then `npx supabase start -x vector` from the repo root,
plug in the phone, the two `adb reverse` lines, then from `mobile\`:
```powershell
npx expo start --dev-client --port 8081
```
and the launch command from step 5.4. The full checklist is "Every day"
in `docs/running-locally.md`.

- **A second user at the same time** (chat, likes, join requests): open
  http://localhost:8081 in a browser on the computer while Metro runs,
  and log in as another test account.
- **Emails** (sign-up codes, password resets, Room domain verification)
  arrive in Mailpit at http://localhost:54324.
- **Stopping:** `npx supabase stop` keeps the data. `--no-backup` deletes it.

---

## 7. Check that everything works

From `mobile\`, the same three checks CI runs on every push:
```powershell
npm run lint
npm run typecheck
npm run check:compiler
```

From the repo root, the backend security re-check (537 checks, a few
minutes; `supabase/tests/README.md`):
```powershell
node supabase/tests/run.js --live
```
It runs only against the **local** stack, using the test accounts, and
cleans up after itself. Run it after any change to a migration, policy,
grant or Edge Function. **Never point it at the hosted project.**

The app has no unit-test runner. Real verification is using the change on
the phone against the local stack, as the write-ups in `docs/phase/`
describe.

## 8. Push notifications and builds (needs the project's accounts)

Pushes go from the database to an Edge Function, then through Expo's push
service and Firebase (FCM) to the phone. They need:
- a development build (step 5), never Expo Go;
- the EAS project named in `mobile/app.json` (`owner: thenujacode`, its
  `projectId`), which you must be a member of;
- the Firebase **service account key** uploaded to that EAS project in
  the **"FCM V1 service account key"** slot. There's a similar-looking
  slot for EAS Submit that does nothing for push (decision-log,
  2026-08-15).

Without access to those accounts, everything else works and pushes are
silently not delivered. To run your own copy, you'd create your own
Firebase and EAS projects and change `owner`, `projectId`, the Android
package name and `google-services.json` to match.

Release builds and the signing key are covered in the "APK Beta Phase" of
`docs/roadmap.md`.

## 9. The hosted project (production)

Only for whoever holds the Supabase account. **The full runbook is
`docs/hosting.md`,** which also rebuilds the project from nothing. In
short:

- Project `bihcnyzempsvwhklegkl`, Singapore, free plan. Email goes out
  through **Resend** from `noreply@chasien.com`. DNS for `chasien.com` is
  at **Namecheap**.
- **Log the CLI in** from a normal terminal: `npx supabase login`. The
  CLI refuses to log in from inside an AI coding agent (see "The CLI" in
  `hosting.md`).
- **Create `supabase/.env.hosted`** with `SUPABASE_DB_PASSWORD=` and
  `RESEND_API_KEY=`, from the password manager.
- **Commands that target the hosted project need `--remote`**, or they
  act on the local stack.
- **Never** run `seed.sql` or `supabase/tests/run.js` against it. The
  test accounts all use `password123`.
- **To run the app against it:** create `mobile/.env.development.local`
  with the hosted URL and its legacy anon key, then restart Metro with
  `--clear`. Delete the file to go back to local (`hosting.md`, step 8).

## 11. When something goes wrong

Every environment problem hit so far is in **"Known gotchas" in
`docs/running-locally.md`**, with the fix. A quick map:

| Symptom | Gotcha |
|---|---|
| `supabase start` fails, or Docker answers with errors while `docker info` looks fine | #1 |
| The app is stuck on "Reloading…" | #2: launch it on `localhost` |
| The phone isn't in `adb devices` | #3 |
| Port 8081 is already in use | #4 |
| The native build fails with a "restricted method" error | #5: set `JAVA_HOME` |
| `supabase start` downloads GB of new images | #9 |
| Every Edge Function returns 503 after the repo folder moved | #10 |
| A new Edge Function, or a `config.toml` change, doesn't take effect | #9, #11 |
| An edited Edge Function still runs the old code | #13 |
| Pushes and cleanups silently don't happen | #16: the Vault secrets |
| `npm ci` says "Missing … from lock file" | Regenerate the lock with a current npm (decision-log, 2026-09-22) |
